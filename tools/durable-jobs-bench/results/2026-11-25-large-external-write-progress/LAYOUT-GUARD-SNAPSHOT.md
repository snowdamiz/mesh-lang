# A checked helper can change within the same READ COMMITTED call

On PostgreSQL 17.11, the stock `enqueue_batch_layout_v1()` fingerprint returned true before a barrier in a volatile function. The worker held the same shared migration advisory lock used by the public bulk writer. A second connection, logged in as the ordinary schema owner, tried the matching exclusive advisory lock and was refused. It then replaced `effect_key(mesh_jobs.jobs)` using ordinary transactional DDL. After the barrier, the original worker’s function called the replacement and returned its new value. The next fingerprint returned false.

This matters for LARGE streaming because the eager function renders the full grant before PostgreSQL converts the first output row to the final client encoding. A custom helper can change that encoding during a later row. Testing the helper fingerprint before streaming cannot exclude a definition installed while the call is in progress. The witness uses a wrapper to position the barrier inside one volatile statement. It establishes the scope of the proposed fingerprint check and does not modify the released prepare function. Run `python3 -B layout_guard_snapshot.py --pg-bin /opt/homebrew/opt/postgresql@17/bin | cmp - layout-guard-snapshot.json` from this directory. The proof creates a disposable socket-only cluster under the checkout, installs the frozen public schema as a non-superuser owner and runs the checked call under a separate login.
