# Dense completion batching with hot application connections

In six earlier native rotations the hot, writer-off Mesh runner used 841–866 terminal transactions for 1,024 jobs. River used 11–14, Apalis 52–56, and Oban 1,024. Cold Mesh with an asynchronous zero-hold writer used 645–709, while its median drain fell to 749 jobs/s from 773 and 776 in the duplicate controls. Each job in every arm committed both application writes independently. The per-arm counts and source archive hashes are in [reference.json](reference.json).

This diagnostic tests whether a one-millisecond batching window on already confirmed completions improves the whole queue when the hot application pool is enabled. Two opposite orders use the same Mesh runner ELF, producer, and handler for both writer-off duplicates, zero hold, and one millisecond. All seven lanes use two runners with 32 slots each and share CPUs 0 and 1 with PostgreSQL. The scorer verifies each warmup before the measured arms can run.

Run `python3 -B controller.py check` in this directory to check source hashes, the generated adapter, all seven inventories, and rejection of an archived writer-off arm passed as an enabled writer. The controller runs `python3 -B controller.py timing 1 2` in its exclusive slot, followed by `python3 -B controller.py replay`. The two-group screen requires earlier last application writes and fewer terminal transactions than all controls. Submit, drain, and the middle 820 second writes must each improve by more than both 5% of the fastest control and the difference between the identical controls in each group. Any positive diagnostic needs replicated workload results and native fault checks of the exact combined settings before adoption.
