# Dense jobs heap fillfactor on PostgreSQL 17.11

A jobs-table fillfactor of 50 caused all 64 claim and completion transitions in the structural proof to stay on the same heap page. All 64 records reused a 1,185-byte WAL prefix that covered the full 1,110-byte inline argument. The last byte of the argument was at offset 1,174 in the tuple data. Every transition used an ordinary heap UPDATE. The two default controls produced a combined 3 of 64 same-page claims and 29 of 64 same-page completions in the retained receipt. [Raw TIDs, flags, and block data](evidence/structure.json.gz)

The proof used the first 32 jobs from the checksummed public dense batch. It applied the frozen b3557273 DDL to three empty PostgreSQL 17.11 databases, ran the bulk writer as the producer role, and claimed and settled two groups of 16. Each control used the same replacement guard. That guard accepts the exact one-element jobs reloption array `{fillfactor=50}` or the original defaults. The fixture requires default argument storage. The rest of the stock layout fingerprint and the original role grants remain in effect. Ten rollback controls per layout cover extra or different reloptions, TOAST reloptions, a queue fillfactor, column defaults, storage and compression, index creation and index reloptions, and disabled triggers. Each returned the stock fallback sentinel before writing jobs, queues, or receipts. A wrong settlement token affected zero jobs. [Installer](layout.py) · [Untimed proof](prove.py)

PostgreSQL 17.11 uses the prefix and suffix flags when the new tuple lands on the same page, logical decoding does not require a complete new tuple, and the record does not need a new full-page image. This mechanism works with ordinary indexed UPDATEs. The prior EXTERNAL storage experiment produced no change in the inline tuple, and the traced claim study did not isolate heap representation from other WAL sources. ## Controller pilot

The packet stages two opposite orders of duplicate default layouts and fillfactor 50. Each block includes canonical warmup and measured arms. It uses the measured public grouped-settlement hot 2×32 deployment, ELF `af2aca86…` and its original producer. The frozen scorer checks verified TLS, the pinned PostgreSQL build, boot and two CPUs, 1,024 canonical jobs, eight bulk writes and zero scalar fallbacks in one enqueue transaction, two independent application XIDs per job, grouped settlement, and drained runner teardown. The observer also checks terminal token state. Only the owner fixture changes. The original launcher retains the native lock and privilege drop. [Controller packet](controller-packet.json) · [Archived hot reference](../2026-11-24-dense-product-d2-transfer/NATIVE-RESULTS.md)

The pilot introduces no statements during the timed interval and changes no server settings. It records the live relation counters after every workload client exits. Those counters can lag and are treated as auxiliary whole-arm observations. The exact physical witness is a relation-filtered WAL dump from the pre-workload insert LSN to the post-teardown insert LSN, decoded after clean shutdown. It counts 1,024 heap inserts and 2,048 heap updates and reports whole-arm same-page, prefix, suffix, HOT, full-page image, and record-byte counts. It has no per-phase attribution. The installed Linux PG17.11 `pg_waldump` and the relation's `n_tup_newpage_upd` column must pass the native gate. Both interfaces worked on the local PG17.11 proof. The retained Linux evidence does not establish the decoder file's availability. The adapter archives its hash and version or fails closed before the workload if the binary is missing. [Native observer](observe.py) · [PostgreSQL statistics publication](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/utils/activity/pgstat.c)

Both measured fillfactor arms must beat the faster duplicate by more than 5% and the duplicate spread on full submit-to-settlement and enqueue-commit-to-settlement. The last application effect must beat both duplicates by more than the spread on both corresponding clocks. The candidate must show more same-page heap updates and prefix records than either control. CPU use is capped at 110% of the higher control, independently for the runners and the two pinned CPUs. Final heap size, total jobs relation size, and the highest WAL-referenced heap page are capped at 125% of the larger control. The insert records also bound the heap pages touched at enqueue, which may reach 210% of the larger control. In the cold structural cohort the available heap grew from 24 to 48 KiB and the completed heap shrank from 56 to 48 KiB. Any four-engine comparison would disclose the optional PostgreSQL tuning and measure its footprint. Only two passing blocks and a clean controller release open pricing for that comparison.
