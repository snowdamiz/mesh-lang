## Concrete connection state and admission

Retain private CoreConnectionSetting { BusyTimeout1000, SecureDeleteOn }. These are operation operands, never permits. Add one stable Box<ConnectionCallbacks> owned by SqliteConn for its entire native connection lifetime. The box contains an authorizer policy cell (Ordinary or exact CoreSetting), a configured busy policy (Disabled or Budget1000), and an optional active-operation budget. Access is confined to the retained connection mutex and synchronous SQLite callbacks on that same thread. The callback reads these cells directly; it cannot lock the connection recursively. No callback points into a temporary Rust guard, Mesh stack or JNI frame.

An active budget contains one monotonic deadline and a retained original InvocationContext for the exact admitted operation. Its guard is established inside FixedEffect::execute after authority::perform admission, and cleared before local settlement ends. The callback only borrows that retained context. It never clones/drops the final owner inside C, acquires authority or consults a process count as permission. Final owner disposal happens outside C and runtime registry locks. One SqlPrepare budget and one separate SqlStatement budget each start inside their admission; query rows, locking events, busy-count resets and internal reprepares do not reset a budget. No whole-public-call 1000ms promise follows from these two admissions.

## D1: recovery obligation precedes canonical timeout preparation

Before calling sqlite3_prepare_v2 for the canonical timeout setter, install a TimeoutRecovery guard while holding the connection, inside admitted SqlPrepare execution. It records the prior safe configured policy and owns the obligation to replace or disable SQLite's handler on every outcome. No early return, error extraction, outer Rust unwind or partial statement cleanup can bypass that obligation. Guard ordering keeps callback storage and active budget valid through partial/final statement destruction. Cleanup must leave no stock handler available to another operation before unlocking or ending settlement.

On successful prepare, select Budget1000 and install the runtime busy callback. On a failed prepare, restore the prior safe configured policy: Disabled for first configuration, or the prior Budget1000 for reconfiguration. This is explicit error behavior; it does not claim SQLite rolled back a prepare-time setter. A failed secure-delete prepare may likewise already have applied ON; never compensate by disabling secure deletion.

The guard always attempts installation of the runtime handler with stable userdata, including after a prepare failure that happened after SQLite installed its stock timeout callback. If installation reports failure, disable waiting with a null busy callback and return an application error. If disabling also fails, poison the connection, remove it from public lookup and dispose it under its retained owner; never return it as reusable. Cleanup must not panic or unwind through C. Keep its storage until SQLite can no longer invoke it. No restoration by calling sqlite3_busy_timeout is permitted: that would reinstall the stock handler. Callback policy Disabled or absent active budget always returns zero. No operation may borrow an expired deadline.

All prepared statements are finalized while the retained connection and callback box remain live. Rollback on disposal has no active budget and therefore no waits. Before destroying callback storage, unregister authorizer and busy callback while the database is still valid, after ordinary statement cleanup; then close it. Current source uses sqlite3_close, not close_v2. A non-OK close must not free userdata still registered with a surviving native connection: successful unregistration is required first, otherwise retain the connection and storage in fail-closed disposal ownership and report the cleanup failure. No deferred zombie-connection assumptions. Fault tests must cover this policy, including close racing a retained active statement; removal of a registry handle alone never frees that connection.

Within canonical preparation the stock timeout setter can replace the callback before prepare returns; the recovery guard closes every exit from that admitted call. The supported SQLite/VFS assumptions below rule out foreign reentry during this interval. No later statement, retry or user callback may use that stock handler. A fault after the setter and before prepare return is a mandatory test, not presumed impossible.

## D2: one stable authorizer registration

Install the protected authorizer once when opening the scoped connection, with the stable ConnectionCallbacks pointer. Do not call sqlite3_set_authorizer to enter or leave a setting policy: registering even the same callback expires statements and could cause reprepare at ready-step.

A PreparePolicyGuard enters only from Ordinary, only inside admitted canonical prepare. Nested configuration is rejected fail closed before preparing or changing state, leaving the outer state intact. The guard restores exactly Ordinary on success, failure and outer Rust unwind. It mutates only the state cell and never changes callback registration. Its privilege ends before returning a prepared statement. Authorizer acceptance requires the exact enum's name/value, unqualified database argument, canonical origin and no unexpected trigger/source; ordinary rules otherwise remain unchanged.

Separate ready-step admission runs with Ordinary policy. The two canonical statements must prepare and then step successfully without forced expiration. Unexpected automatic reprepare of a configuration statement receives ordinary PRAGMA denial, marks sticky authority refusal and returns failure; no setter allowance, retry or silent replay is installed. Ordinary statements retain ordinary authorizer rules during internal reprepare. A forced-expiration test must prove the setter is not reapplied and the custom busy handler remains installed. Calling sqlite3_set_authorizer only for final unregistration happens after all statements have finished and grants no execution privilege.

## Exact inputs, statuses and waits

Validate original connection ownership, actual autocommit, execute mode, empty decoded parameters and any typed-V2 quota before selecting or preparing either setting. Cover text, typed and typed-V2 execute AND query paths. Recognize the full Mesh byte string, including embedded NULs, before constructing canonical runtime SQL. Bound total input before ASCII-only outer trim; the proposed initial bound is 128 bytes, permitting only space, tab, CR and LF outside the two exact internal spellings. Reject case/spacing alternatives, comments, semicolons, suffixes/second statements, qualifiers, quotes, alternate values and bound parameters. The two setters on query paths refuse before preparation. This does not change or claim to reject every ordinary SQL tail currently ignored by legacy code.

Preserve actual execute result behavior (sqlite3_changes); no invented rows-changed or PRAGMA readback. Installing a custom handler resets SQLite's busyTimeout introspection to zero; query/readback remains denied. Policy violations set sticky authority refusal; live-authority contention and native application errors remain distinguishable internally. No new public ABI status or private error publication is introduced.

Sample sqlite3_get_autocommit under the connection lock before entering C. The busy callback checks that sampled state and the original invocation's transaction/resource counters, including transactions on other connections. No wait while an explicit transaction or another resource scope is held. Local settlement is not a resource lock or permission: do not require local_inflight==0, subtract guessed own resources, or treat the unavoidable connection/SQLite locks as another external resource. If implementation adds its own resource guard it must distinguish that guard structurally.

The callback cannot call SQLite, Mesh/Host/JNI, acquire runtime locks, finalize, close, schedule work, park/yield or unwind. Check original liveness and fixed remaining deadline before each bounded native sleep and again after it before returning nonzero. No automatic transaction or statement retry. Retiring during a controlled sleep must prevent that callback's post-sleep retry. A retirement after the final successful scan may lose to that already-admitted operation; do not promise no write after cancel returns. Settlement persists until C and operation-owned cleanup finish.

SQLite can return BUSY without invoking the callback to avoid deadlock; releasing a lock within budget is not universal success. Native sleep occupies the single scheduler lane. An actor needing that lane cannot release a lock during this wait; expiry/no-wait must restore progress. The aggregate deadline bounds permitted retries, not OS scheduling, filesystem stalls or SQLite work that does not call the handler. Existing VM bounds remain.

## Secure deletion and supported native configuration

The actual ON setting acts on the configured connection's Btrees; it is not persistent and cannot be replaced with FAST or a no-op. Deletion durability follows the admitted deletion and commit/journal/fsync behavior. Retain explicit exclusions for old WAL/journal copies, backups, snapshots and flash remnants. Core closes its schema connection; this setter does not secure every subsequent connection or deletion. A typed initializer migration across app connections needs separate authorization.

This prerequisite assumes SQLite shared-cache remains disabled for the process, no externally supplied VFS/extension or native code reenters these connections, and no external code replaces their callbacks. Current open does not force PRIVATECACHE. State and verify these preconditions in fixture/embedding qualification; do not claim unconditional connection isolation if arbitrary native code enables shared cache. Enforcing PRIVATECACHE would be a separately reviewed source choice. No global configuration mutation is authorized here.
